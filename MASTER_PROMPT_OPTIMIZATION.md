# MASTER PROMPT — SKLADAPLAN / ОПТИМИЗАЦИЯ СКЛАДА

Ты работаешь с существующим production-проектом SKLADAPLAN (vanilla HTML/CSS/JS + Supabase). Не переписывай приложение и не ломай существующие модули.

## Цель
Добавить раздел «Оптимизация склада», который анализирует актуальные данные основной таблицы `boxes`, строит физически выполнимый план консолидации коробок между зонами и после подтверждения одним действием применяет весь план в Supabase.

## Бизнес-правила
1. `1 barcode = 1 physical box`. Никогда не превращать дубли barcode в количество.
2. Вместимость стандартного паллета по умолчанию — 40 физических коробок; пользователь может изменить лимит перед расчётом.
3. Источник: одна или несколько выбранных зон/рядов.
4. Цель: одна выбранная зона/ряд.
5. Можно оптимизировать все подходящие неполные паллеты либо только выбранные пользователем исходные паллеты.
6. Перемещаются только физические коробки со статусом `На складе`.
7. Нельзя трогать `КПодбору`, `Скомплектовано`, `Отгружено`, `Зарезервирована` и другие статусы.
8. В целевой паллет можно добавлять коробки только если он открыт/доступен и после перемещения не превышает вместимость.
9. Для безопасности консолидация выполняется только внутри одного склада.
10. Не смешивать разные `Артикул` на одном целевом паллете. Целевой паллет допускается только если его существующие коробки имеют тот же артикул, что и перемещаемые коробки, либо он пустой.
11. Не создавать новые физические паллеты автоматически: если подходящей ёмкости в целевой зоне нет, это должно быть отражено в отчёте как «не удалось разместить».
12. План расчёта не меняет БД.
13. Кнопка «Закрыть оптимизацию» применяет весь утверждённый план одной атомарной серверной операцией. Если хотя бы одна проверка не проходит, изменения не применяются.
14. После успешного закрытия в `boxes` должны быть новые `Склад`, `Зона/ряд`, `Поддон`, а также соответствующие FK, если они существуют.
15. Каждое физическое перемещение записывается в `box_movements` с причиной `optimization`.
16. Должна сохраняться история самой оптимизации и её операций.
17. Перед применением сервер должен проверить, что исходное состояние коробок не изменилось после расчёта. Если изменилось — вернуть конфликт и не применять ничего.

## Алгоритм
- Получить свежие данные из Supabase.
- Сгруппировать физические коробки по `Склад + Зона/ряд + Поддон`.
- Найти исходные неполные паллеты (< capacity).
- Для каждой исходной группы подбирать целевой паллет в выбранной зоне:
  - тот же склад;
  - тот же артикул;
  - свободная ёмкость;
  - паллет не закрыт.
- Приоритеты подбора:
  1. максимально заполнить существующий целевой паллет;
  2. полностью освободить исходный паллет, если это возможно;
  3. минимизировать число физических перемещений;
  4. при равенстве — использовать целевой паллет с большей текущей заполненностью.
- Разрешать частичное перемещение исходного паллета, если целевой паллет не вмещает всё содержимое.
- Один barcode = одна перемещаемая запись.
- Не создавать план с дублирующимся box id.

## Интерфейс
Добавить в sidebar отдельный раздел «Оптимизация склада».

Экран должен содержать:
- склад;
- исходные зоны/ряды (multi-select);
- целевую зону/ряд;
- вместимость паллета, default 40;
- режим «Все подходящие паллеты / Выбранные паллеты»;
- список исходных паллет с количеством коробок и возможностью выбрать;
- кнопку «Рассчитать оптимизацию».

После расчёта показать:
- количество исходных паллет;
- количество целевых паллет;
- количество коробок к перемещению;
- сколько исходных паллет будет полностью освобождено;
- сколько мест останется;
- сколько коробок не удалось разместить;
- подробный рабочий отчёт.

Отчёт:
`№ | Откуда | Исходный паллет | Артикул | Коробок | Куда | Целевой паллет | Было → станет`

Должна быть возможность снять отдельные операции из плана перед закрытием.

Кнопки:
- «Пересчитать»;
- «Экспорт отчёта»;
- «Закрыть оптимизацию».

После закрытия:
- показать итог;
- обновить локальные данные из Supabase;
- очистить временный план;
- не считать операцию закрытой, если RPC вернула ошибку.

## Безопасность
- Применение только для admin.
- Использовать `security definer` RPC с явной проверкой `skladaplan_is_admin()`.
- Не давать браузеру прямой UPDATE boxes для закрытия оптимизации.
- RPC должна работать транзакционно.
- Проверять целевой склад/зону/паллета.
- Проверять исходные warehouse/zone/pallet и количество выбранных box ids.
- Проверять capacity до изменения.
- При любой ошибке `raise exception` → PostgreSQL откатывает всю транзакцию.

## Совместимость
Не менять существующие `sp_move_boxes`, `sp_merge_pallets`, сборку, приёмку, отгрузку, планировщик, задачи, импорт Excel и карту.

Использовать существующий минималистичный UI SKLADAPLAN.

## Проверки перед завершением
1. Синтаксис JS.
2. Отсутствие дублирования глобальных функций/ID.
3. Проверка навигации desktop/mobile.
4. Проверка расчёта на искусственном наборе данных.
5. Проверка: 10 + 20 + 30 коробок → целевые ёмкости 10/20 и capacity 40.
6. Проверка разных артикулов.
7. Проверка отсутствия свободной ёмкости.
8. Проверка частичного перемещения.
9. Проверка stale-plan conflict.
10. Проверка SQL/RPC по тексту и согласованности типов bigint.
11. Проверка, что закрытие создаёт историю и меняет `boxes`.
12. После всех изменений собрать ZIP проекта без `.env`/секретов.
