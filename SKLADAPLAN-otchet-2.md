## 1. Боковое меню — подсветка и значок

### Что было не так

CSS-геометрия после первого этапа была в порядке (иконки не двигаются), но выделение и значок действительно могли выглядеть раздельно: у активного пункта фон становился чёрным, а линия иконки оставалась тёмной — значок «выпадал» из подсветки.

Причина в том, как цвет доходил до SVG. Иконки лежат в спрайте и подставляются через `<use href="#icon-...">`. Цвет им задавался только наследованием — `stroke: currentColor` на `.icon` и `color: #fff` на `.nav.active`. Внутри теневого дерева `<use>` этот унаследованный `currentColor` в части браузеров (заметнее всего в WebKit на iOS, но встречается и в десктопном Safari) не пересчитывается при смене класса на родителе. Плюс у нескольких символов спрайта (`icon-divide`, `icon-help`, `icon-more`, `icon-list`) внутренние точки залиты `fill="currentColor"` — их одна только правка `stroke` не покрывала вообще.

### Как исправлено

Цвет активного состояния теперь задаётся **явно**, а не только наследуется:

```css
.nav.active .nav-icon,
.nav.active .nav-label,
.nav.active > span { color: #fff; }

.nav.active .icon { color: #fff; stroke: #fff; stroke-width: 1.95; }
```

То же самое для мобильной панели (`.mobile-nav-btn.active`). Геометрия по-прежнему не меняется ни в `:hover`, ни в `.active` — только цвет, фон и толщина линии.

Если после деплоя картина не изменится — почти наверняка кэш: `style.css` отдаётся Vercel с долгим кэшем. Проверьте жёстким обновлением (Ctrl+Shift+R, на iOS — через «Очистить историю и данные» или приватную вкладку).

## 2. «Задачи» и «Планировщик» — снова два раздела

Разделение восстановлено. Объединение отменено полностью.

| раздел | модуль | таблица | что это |
|---|---|---|---|
| **Задачи** | `tasks.js` | `public.tasks` | список дел: чек-лист, избранное, фильтры, свой календарь |
| **Планировщик** | `planner.js` | `planner_shipments`, `planner_tasks` | календарь отгрузок и планов склада |

В сайдбаре два отдельных пункта. Главная и кнопка «Все задачи →» ведут в «Задачи», как раньше. Алиас `tasks → planner` из `goToPage()` убран.

### Связь между ними — в календаре

Планировщик **читает** уже загруженный `tasksState` из `tasks.js` и показывает задачи с назначенной датой (`due_date`) рядом со своими:

- в клетке календаря они добавляются к общему счётчику задач;
- в панели выбранного дня появляется отдельная секция «Задачи из раздела «Задачи»» — карточки помечены пунктирной рамкой, с кнопкой перехода в раздел «Задачи»;
- редактировать их в Планировщике нельзя намеренно — они правятся там, где созданы.

Копирования данных нет: Планировщик читает тот же массив в памяти, второй копии задач не появляется. Обратная ссылка тоже есть — на странице «Задачи» в панели вида добавлена кнопка «В планировщик».

Чтобы связь работала с первого открытия любой из двух страниц, при входе теперь грузятся обе стороны: `loadTasksFromSupabase()` и `plannerLoadFromSupabase(false)`.

## 3. Счётчик в календаре

Клетка дня теперь показывает **по одному маркеру на вид события**, а не по маркеру на запись:

- 🚚 иконка + число — отгрузки;
- ☰ иконка + число — задачи (задачи Планировщика **плюс** задачи из раздела «Задачи» на эту дату, одним числом).

Сколько бы задач ни было на дне, чип остаётся один — меняется только цифра. У чипа есть `title` с расшифровкой при наведении.

## 4. «Собрано» — формирование поддонов к отгрузке

Новый блок на странице «Собрано», по умолчанию свёрнут (кнопка «Формирование поддонов к отгрузке»).

### Как работает

1. **Направление** — выпадающий список из направлений скомплектованных коробок. Если выбрано, сканер не примет коробку с другим направлением и скажет, с каким она.
2. **Приставка** (необязательно) — например `ОТГР-`, чтобы номера поддонов отгрузки не путались со складскими. Итоговый номер = приставка + номер.
3. **Поддон №** — просто `1`, `2`, `3`... Кнопка «Новый поддон» ставит следующий свободный номер сама.
4. **Сканирование** — поле с автофокусом, штрихкод + Enter. Коробка попадает в текущий поддон.
5. Ниже — список сформированных поддонов: номер, количество, все штрихкоды. Любую коробку можно снять крестиком, любой поддон — убрать целиком.

### Проверки при сканировании

- штрихкод должен найтись **среди скомплектованных** (не среди всего склада);
- направление должно совпадать с выбранным;
- одна коробка не может попасть на два поддона — если уже разложена, сканер скажет, на каком она.

### Кнопки

| кнопка | что делает |
|---|---|
| **Сформировать поддоны** | записывает номера поддонов коробкам, по одной операции на поддон |
| **Переместить на склад** | переносит все отсканированные коробки по адресу склад / зона / поддон из полей ниже |
| **Вернуть на склад** | возвращает статус «Скомплектовано» → «На складе»; коробки уходят из «Собрано» обратно в остаток |
| **Очистить черновик** | сбрасывает набранное, в базе ничего не меняется |

### Важное про безопасность данных

- **Пока идёт сканирование, в Supabase не уходит ничего.** Всё лежит в `state.collectedPalletBuild`. Запись — только по явной кнопке, с подтверждением и превью («какой поддон — сколько коробок»).
- Запись идёт через **уже существующую** RPC `sp_move_boxes` — ту же, что использует раздел «Перемещение». Поэтому история в `box_movements` пишется сама, а правило «1 штрихкод = 1 физическая коробка» не нарушается. Новых RPC и новых таблиц не создавалось.
- Операции формирования помечаются в истории как `reason = 'pallet_build'` — их видно отдельно от обычных перемещений.
- «Вернуть на склад» меняет **только** статус, с защитой `.eq('Статус', 'Скомплектовано')`, чтобы случайно не задеть уже отгруженное. `collected_at` / `collected_by` не обнуляются — история комплектации остаётся.

## 8. Что нужно проверить руками

1. **Выполнить `supabase_migration_planner_favorite.sql`.** Без неё звёздочка на карточке задачи в Планировщике вызовет ошибку.
2. **Если выполняли `tasks_unify`** — разобраться с дублями по инструкции в п. 5 выше.
3. **Сайдбар — жёсткое обновление страницы.** Если значок по-прежнему не подсвечивается вместе с фоном, напишите, в каком браузере и на чём (десктоп/iPhone/Android) — при явно заданных цветах остаётся очень узкий круг причин, и по браузеру я смогу назвать её точно.
4. **Формирование поддонов — на паре коробок, не на всей отгрузке.** Пройдите цикл: отсканировать → «Сформировать» → посмотреть в «Базе», что номер поддона встал как ожидалось. Только потом на реальном объёме.
5. **«Вернуть на склад»** — проверить на одной коробке, что она уходит из «Собрано» и появляется в остатке с правильным адресом.
6. Решить, нужна ли приставка к номеру поддона. Если в вашей практике номера отгрузочных поддонов и складских не пересекаются — поле можно оставить пустым, тогда будет просто `1`, `2`, `3`.
7. Сканер в поле ввода настроен на Enter в конце штрихкода — стандартное поведение, но если ваш сканер шлёт Tab, скажите, добавлю.
