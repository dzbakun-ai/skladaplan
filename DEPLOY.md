# SKLADAPLAN — что в этом архиве и что делать перед деплоем

## Порядок деплоя (важно соблюсти именно так)

1. **Сначала** выполните `supabase_migration.sql` целиком в Supabase
   (Project → SQL Editor). Он аддитивный (`IF NOT EXISTS` везде, где
   можно), ничего не удаляет — но рекомендую сначала прогнать на
   тестовом проекте/копии или сделать backup.
2. **Только после этого** деплойте новый `app.js`/`index.html`.

Если сделать наоборот (сначала выложить `app.js`) — приложение
перестанет загружать коробки вообще: `BOX_SELECT` теперь запрашивает
колонки `collected_at/collected_by/shipped_at/shipped_by`, которых
до миграции не существует.

Я не выполнял миграцию сам — у меня нет доступа к вашей живой базе,
поэтому весь SQL нужно прогнать и проверить вручную.


## Что реализовано в этом релизе

### Этап 1 — поиск и сканер
- Поиск в Базе больше не теряет фокус/клавиатуру при вводе
  (частичное обновление результатов вместо полной перерисовки
  страницы на каждый символ).
- Сканер в Приёмке/Инвентаризации/Сборке проверен — уже был
  безопасен (`inputmode="none"`), менять не потребовалось.

### Этап 2 — атомарные комплектация и отгрузка
- `completeSelectedAssembly()` и `shipSelectedCollected()` теперь
  вызывают RPC (`sp_collect_boxes`, `sp_ship_boxes`) вместо прямых
  `UPDATE` — одна операция на всю партию: либо перешли все
  выбранные коробки, либо (при ошибке) ни одна.
- На `boxes` появились `collected_at`, `collected_by`,
  `shipped_at`, `shipped_by` — раньше была только `updated_at`,
  которая перезаписывалась любым другим изменением.

### Этап 7 — «Собрано»
- Фильтр по дате комплектации: сегодня / вчера / период.
- Статистика: всего собрано за период + разбивка по направлениям.
- Кнопка «Проверка скомплектованного» — выбор направления →
  ожидаемый список → сканирование → результат (совпало / лишние /
  отсутствующие), сохраняется в новые таблицы
  `collected_verification_sessions` / `collected_verification_items`.

### Этап 4 — «Перемещение» (новая вкладка)
- Сканирование коробок по одной, либо выбор целой паллеты одной
  кнопкой, либо автоподхват уже отмеченных чекбоксами в Базе.
- Новое место (склад / зона / поддон) — атомарно через RPC
  `sp_move_boxes`, с записью истории в новую таблицу
  `box_movements`.

### Этап 3 — объединение неполных паллет
- Внутри Инвентаризации: кнопка «Объединить неполные паллеты» —
  выбор нескольких исходных паллет → выбор целевой → подтверждение
  → RPC `sp_merge_pallets` переносит все коробки на целевую паллету
  атомарно, исходные помечаются пустыми/архивными
  (`pallets.status = 'Пустой'`, `pallets.archived_at`).

### Справка (`help.js`)
- Точечно обновлена: добавлен раздел «Перемещение», дополнены
  разделы «Собрано», «Убыло», «Инвентаризация» под новые функции.
- Полного визуального редизайна справки (карточки/иконки/поиск по
  справке и т.д. — Задача №9 из исходного ТЗ) в этом релизе **нет**.
  Сознательно не делал одновременно с изменением бизнес-логики —
  чтобы не смешивать в одном релизе риск разного типа.


## Что сознательно НЕ сделано в этом релизе

- **Разбиение `app.js` на модули** (Задача №8). Файл остаётся одним
  файлом. Это осознанное решение: у меня нет способа протестировать
  многофайловую версию в вашем реальном окружении (Vercel + реальные
  сканеры + реальная Supabase), а риск тихо что-то сломать при
  переносе кода без пошаговой проверки — выше, чем польза от
  структуры прямо сейчас. Могу сделать это отдельным, отдельно
  тестируемым этапом, если скажете.
- **Полный визуальный редизайн справки** — см. выше.
- Реальная эксплуатационная проверка на сканере/телефоне — я
  проверял логику через автоматические тесты (jsdom-симуляция
  DOM/событий), а не через реальное устройство. Перед тем как
  выкатывать на весь склад, стоит пройти основные сценарии руками
  на одном телефоне со сканером.


## Как я тестировал (без доступа к вашей реальной базе/устройствам)

Три автоматических сценария на jsdom (симуляция браузера в Node,
без реального Supabase — подставлял моки):

1. Посимвольный ввод в поиск Базы — поле не пересоздаётся,
   фокус не пропадает, список фильтруется корректно.
2. «Собрано»: фильтр по дате, статистика, полный цикл проверки
   скомплектованного (сканирование ожидаемой и лишней коробки,
   сохранение результата).
3. «Перемещение» + «Объединение паллет»: выбор паллеты целиком,
   перемещение через RPC, объединение двух паллет через RPC —
   с проверкой, что нужные RPC действительно вызываются с верными
   параметрами.

Это подтверждает, что код работает согласованно сам с собой и
не содержит синтаксических/логических ошибок в путях, которые я
проверял. Это **не замена** проверке на реальной Supabase-базе и
реальном сканере — перед полным переключением склада на новую
версию рекомендую день-два поработать на ней параллельно со старой
(или хотя бы одним оператором), особенно для перемещения и
объединения паллет — эти операции необратимо меняют данные.

## Открытые вопросы, которые всё ещё не решены

Эти вопросы поднимались в первом анализе и не были закрыты — они не
блокировали текущий релиз, но важны для дальнейшей работы:

1. Таблицы `orders`/`order_lines`/`pick_items`/`directions`/
   `movements`/`verification_sessions`/`verification_items` в вашей
   Supabase — заготовка на будущее или неиспользуемый остаток? Этот
   релиз их не трогает и не использует (вместо `movements` заведена
   отдельная `box_movements` с известной мне структурой, вместо
   `verification_*` — `collected_verification_*`).
2. Часть колонок `pallets`/`locations`/`warehouses` мне известна
   только из кода, не из полной схемы — если где-то в RPC ошибся с
   именем столбца, `supabase_migration.sql` покажет ошибку при
   выполнении в SQL Editor (это безопасно — ничего не сломается,
   просто нужно будет поправить конкретную строку и перезапустить).
